# AI 应用工程：业务适配、工具、评测与文档处理

来源：[宝玉讨论与精选回复的覆盖说明](../sources/dotey-ai-ability-discussion.md)。原讨论发表于2025年，本专题工程建议与一手文档核验于2026-10-22。

本节为整理者基于上述讨论设计的学习练习。岗位映射是建议，应以具体 JD 为准。答案不必背诵；优先准备真实做过的证据，没做过就明确说是设计方案。

### 1. 为什么在这个业务环节使用 AI？

**可练的问题：** 给一个你熟悉的后端或测试流程，哪些环节适合 AI，哪些继续使用确定性程序？

**期望回答：** 先说明用户、输入、成功标准和出错代价，再比较规则/检索/人工/模型方案。例如让模型协助分类失败日志，但测试是否通过仍由断言与执行结果判断；对无证据的归因保留「未知」。说明可用数据、延迟与成本约束，给出不适用 AI 的情况。

**追问与证据：** 原流程基线是什么？减少的是哪一类人工操作？是否把复核成本算进去？可展示一小组脱敏输入、原流程结果、改进后结果及失败案例。

**不充分回答：** 「因为 AI 更智能」「上 Agent 就能自动化」。业务收益必须有可检验定义，而不是技术名词。

### 2. 如何把任务拆给 AI，并保留人的责任？

此方向与安全后台开发面试Q6—8交叉，详见[AI辅助开发与测试可信度](ai-assisted-development-and-testing.md#q8-你的-ai-开发工作流)，统一维护需求拆解、最小变更、验证和人的责任，不复制第二套答案。宝玉讨论强调岗位实作；安全后台案例提供一次具体面试语境，两者不是同一份题库。

### 3. Python function 的工具调用，与生成代码再执行，有什么区别？

**来源边界：** 问题来自汇总中的 Xiang；下面是整理者答案，不是其原回复。

**核心回答：** 工具调用通常给模型明确的函数定义/参数约束，由模型提出调用及参数，应用再校验并执行已有实现，把结果回传。模型产生调用请求不等于函数已经执行。生成代码方式则产生需要解释/编译执行的程序，可组合循环、转换等逻辑，但执行边界更大，代码仍需审查和隔离。

**怎么选：** 已知、稳定、涉及明确权限的操作优先考虑受控工具接口；开放式数据处理可考虑受限代码执行。没有脱离场景的「绝对更好」。工具可以被代码调用，两者也可组合。

**后端追问：** 参数校验之后如何检查业务授权？重试会不会重复写入？如何限制可调用函数、超时和资源？怎么记录每次请求、执行与结果？不要对模型生成文本直接 eval/exec 后当成可信执行。

**一手核验：** [OpenAI Function calling](https://developers.openai.com/api/docs/guides/function-calling) 描述由应用处理函数调用并返回结果的流程。接口约束、权限设计和隔离比较属于本练习的工程设计建议，并非官方保证。

### 5. 怎么判断新模型适不适合自己的任务？

**期望回答：** 先固定任务与验收标准，准备独立测试样本，覆盖常见、边界与对抗/异常情况；同样条件比较候选方案，不只选几个讨巧题。记录正确性、任务完成、延迟、费用和错误类型；必要时重复运行并说明波动。

**更强证据：** 样本来源、标注依据、失败分类、改动前后结果，以及提示开发样本与最终测试样本的区分。人工判断题可解释评分规则和分歧处理。

**一手核验：** [OpenAI Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) 建议任务相关评测、典型/边界/对抗样本及持续评估。本文没有采用文档示例中的数值作为通用及格线。

### 6. RAG 回答不对，先改提示词吗？

**期望回答（排查方案）：** 先看知识源是否存在且仍有效、抽取是否丢失关键信息、检索是否找到相关证据、上下文是否带入，再看生成是否忠实使用证据。分别准备「没有正确材料」「材料存在但没召回」「材料召回但答错」的例子，避免把所有错误都叫幻觉。

**应说明的边界：** 这是诊断框架，不是 RAG 自动保证正确的证明。没有证据时可拒答或转人工；访问权限必须由系统控制，不能只写在提示词里。

**练习交付：** 一份小规模公开/虚构文档集、若干问题、预期证据位置、检索结果与最终答案。不要为了演示上传真实公司敏感文档。

### 7. PDF 抽取实战，如何从 demo 做到可验收？

**建议练习：** 使用合成简历或公开许可的非个人示例文档，实现多 PDF 上传、字段抽取、来源定位与只读查询。暂不做录用评分或自动淘汰。

**期望回答：** 区分文本 PDF 和扫描图像；定义字段类型与缺失值语义；保留文档/页码对应关系；处理重复文件、损坏文档和失败重试；让使用者能回查原文。自然语言查询要经过受限查询层，不让模型任意执行数据库写入。

**验收设计：** 字段是否准确、缺失是否诚实、来源是否可定位、错误是否显式展示。按字段和文档类型分析失败，不用「输出 JSON 成功率」冒充事实准确率。

**一手核验：** [OpenAI Structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) 明确指出结构化输出仍可能有内容错误。符合 schema 不等于内容真实；异常输入、拒绝与不完整结果也需要处理。

### 8. 如何说明学习能力，而不是列出订阅工具？

**期望回答：** 讲一个具体循环：发现工作问题 → 查一手资料 → 小实验 → 得到结果 → 记录失败 → 决定保留或放弃。能解释为什么没有选另一个方案，比列举很多品牌更有辨识度。

**证据包建议：** 一份 README、一组可运行示例、一个失败案例、一份评测记录。使用免费 API、公司允许的工具或本地工具都可以；付费金额、设备档次及是否用某国模型不应替代能力证据。


## 深入追问的回答方向

这些是整理者扩展，不是来源回复原文。

- **业务收益怎样证明？** 固定任务和验收口径，与不用模型的基线比较；同时记录人工复核、错误修复、延迟和调用费用。处理速度提高但错判增多不一定产生净收益；不满足必要安全边界时先缩小自动化范围。
- **参数符合schema为何仍不能执行？** schema解决结构与类型的一部分，业务授权、对象归属、状态合法性和副作用预算仍由应用判断。一次格式正确的删除请求也可能越权。对重复请求须定义幂等键和完成状态，超时不等于没有执行。
- **怎样避免评测过拟合？** 区分调提示用的开发集与最终测试集，保留样本来源和标签标准；按任务类别看失败，不能只报平均分。人工评审存在分歧时先校准规则；模型裁判也需抽样人工核验，不将其分数直接当真值。
- **RAG加了更多文档为什么更差？** 检查新增材料是否陈旧、重复、冲突或超出访问范围，以及检索是否把无关材料挤到前面。先定位抽取、索引、召回、上下文装配、生成哪个环节出错，再选重建索引、过滤、重排或生成约束；不默认加长上下文能解决。权限过滤由系统执行，拒答本身也需评估是否误拒。
- **PDF结果缺字段怎么办？** 区分原文不存在、抽取失败、模型漏填及schema允许的空值，输出明确状态和可回查页码。扫描质量低时可保留待人工复核，不编造值填满字段。重复上传与失败重试要以文档标识/处理版本控制，查询层只授予任务需要的权限。
- **没有生产AI项目如何回答？** 如实展示一个小实验的需求、版本、基线、失败案例和限制，说明下一步如何验证规模、稳定性与成本。不用工具订阅或模型名称代替证据，也不把练习写成客户成功案例。
