# 我为什么要亲手做一个 Agent，以及做到哪里就够了

> 这是我接下来可以照着做的学习答案与操作路线，不是一份已经完成项目的经历。2026-11-06 核对了项目源码；配套练习由助手在隔离目录运行，通过 14 项标准库测试。我本人尚未按这份路线实践，真实模型与真实生活服务也尚未接通。

我想做的不是又一个聊天窗口，也不只是一个职业助理。我关心的是：能不能给同一个人配置多个角色不同的 bot，让它们处理工作、研究、衣食住行中的具体事情，把需要选择和承担后果的决定留给人。

但“我想要这样的产品”和“我现在能可靠实现什么”需要分开。角色名字、提示词和一个云桌面，都不能自动带来可靠的执行能力。我需要先把一个任务从输入到结果做通，再决定哪些东西值得抽象成框架。

纳米 AI 的三条建议，我并不需要三选一。我同时是有后端经验的人、需要把项目说清楚的人，也是可能尝试独立产品的人。三条建议分别解决不同的问题。

## 一、三条建议，我分别怎么回答

### 1. 为了面试，我要亲手写什么

我的目标不是背出 ReAct、RAG、MCP 的定义，而是能解释一次真实运行：模型收到什么，为什么选这个工具，参数在哪里校验，失败后状态怎样变化，最后凭什么认定完成。

我会亲手实现一个很小的循环：接收问题，构造上下文，让模型提出动作，校验动作，执行工具，把结果交回模型，最后输出带来源的答案。工具先只有搜索和读取，暂不允许发消息、付款、执行 shell。

这件事值得手写，因为核心难点就在普通后端问题里：输入验证、状态机、超时、资源上限、日志、隔离、幂等和测试。模型只是多了一个不完全可信的决策环节。我不能把模型返回的 JSON 当作已经获得授权的命令。

练习完成后，我希望拿得出四样东西：一次成功运行记录、一次失败记录、自动化测试，以及我主动没有实现的部分及原因。它们比“我熟悉多 Agent”更容易经得住追问。

### 2. 我有后端经验，为什么不把框架全部重写

我已经能理解 HTTP 服务、数据库和任务执行，并不需要靠重写全部组件证明能力。手写最小循环，是为了找到边界；后续应该读成熟框架如何处理我真正遇到的问题。

例如，只有两个只读工具时，我不需要动态工具注册和多 Agent 调度。任务开始跨小时等待用户确认，我才需要可靠的持久化执行。出现多个独立业务角色时，我才需要明确它们共享什么、隔离什么，而不是先搭一套角色聊天系统。

阅读源码时，我要回答的是：这个抽象解决了什么具体痛点？省掉它会在哪里出错？它引入了哪些配置、调试和运维成本？我会读循环、工具执行、权限和上下文管理，先不把整个框架作为学习前置条件。

### 3. 如果做独立产品，我的最小闭环是什么

我不会一开始承诺“私人助理、地产专家、旅行助理都能自主执行”。这意味着同时处理大量网站、账号、地区规则和现实世界失败，范围远超一个练习。

我选择一个生活任务作为第二阶段验证：用户提出聚餐需求，助理整理条件，从模拟数据里找候选，说明取舍，等待用户选择，生成一份待确认的订餐请求。第一版明确不真的打电话、不下单、不付款。

这仍然服务于生活代理方向。它验证的是角色配置、偏好、工具调用、确认和结果展示能否配合工作。模拟闭环跑通之后，再接一个真实渠道，只承诺一个可核验的结果。

我会把几类工作分开：

- **后续迁移方案**：通过服务层读取 Research Question，让 Agent 根据允许访问的研究材料回答。尚未实现。

配套目录：[agent_lab](../practice/agent_lab/README.md)。里面只有标准库 Python 代码，不需要 API Key，不需要装模型，不会读取我的个人文件，也不会连接第三方服务。

```bash

```

要求 Python 3.11 或以上。Windows 使用 `py -3` 替换 `python3`。私有仓库访问使用自己已有的 GitHub 登录，不把 token 写进命令、截图或提交记录。已经有仓库时，不在未知未提交修改上直接拉取；可以另建学习目录。

我应看到 14 项测试通过，以及状态 `completed_unverified`。这里的意思是循环结束、引用通过最低限度检查，**不是答案事实已经验证**。

fake 模式按固定脚本依次执行 search、read、finish。它验证程序的状态和边界，不能证明模型会推理，也不能用于比较模型能力。输出文件使用排他创建，重复运行同名文件会失败，避免覆盖第一次记录。可以改成 second-run.json。

### 我应该怎样读这段代码

按这个顺序看 [agent.py](../practice/agent_lab/agent.py)：

1. DOCUMENTS：目前只有小型固定资料和虚构餐厅数据，不是生产数据。
2. SYSTEM：约定模型能提出的三种动作和 JSON 格式。
3. validate_action：检查字段、类型、长度和工具名称，不允许任意增加参数。
4. execute：搜索与读取的实际实现，没有 shell 或文件路径入口。
5. run：构造上下文、调用模型、记录动作、处理错误和终止。
6. ScriptedModel 与 LocalModel：前者确定性测试，后者是可选的本地兼容接口。
7. main：命令行和结果文件，不承担业务权限判断。

这里刻意采用 JSON 动作协议，而不是某家厂商的原生 tool_calls。好处是能直接看清循环；代价是需要自己处理格式错误。接入原生工具调用时，要按照对应 API 保留 tool call ID 和角色，不能把本练习的 user 消息封装原样搬过去。

### 一次完整运行经过什么

问题进入后，模型先看到系统约束和用户问题。模型提出 search，服务端验证 query，再返回候选资料。模型提出 read，服务端验证 ID，再返回正文。最后模型提出 finish，服务端检查引用的 ID 是否真的成功读过。

搜索命中不能冒充读过正文。即使读过，也只能说明引用存在，并不能证明答案忠实。练习里专门有一个测试：错误答案配上合法引用，依然可能结束，所以状态必须叫 unverified。

这也是我的面试回答之一：**结束条件与业务验收是两层事情**。模型说完成，只是一个事件；结果符合事实、订单真的存在、收件人真的收到，都需要额外证据。

## 四、我必须亲手验证的失败路径

我先运行现成测试，再逐条修改测试输入，观察状态与 trace，而不是只看一条成功输出。

| 场景 | 本练习应如何表现 | 生产实现还缺什么 |
|---|---|---|
| 模型输出坏 JSON | 拒绝动作，反馈错误，受总步数限制 | 分类统计、可靠重试策略 |
| 模型要求未知工具 | 不执行 | 服务端按用户和任务授权 |
| 模型参数多字段或类型错误 | 拒绝 | 更完整的业务约束 |
| 读取不存在的资料 | 返回工具错误 | 权限与不存在情况的适当区分 |
| 直接引用没读过的 ID | 不接受 finish | 引用与答案逐项核验 |
| 模型不停调用工具 | 达到步数上限后停止 | 时间和费用预算、取消机制 |
| 上下文过大 | 达到字符预算后停止 | tokenizer、摘要与来源保留 |
| 模型接口异常 | model_error，不打印可能含秘密的异常详情 | 脱敏诊断、重试和告警 |
| 资料中包含恶意指令 | 没有新增工具执行权限 | 真实模型对抗测试和隔离 |

字符预算不是 token 预算。测试中的“资料恶意指令”只能说明程序不会凭资料新增执行入口，不能证明真实模型不会被提示注入影响。权限边界不能依赖模型自觉遵守提示词。

我还会做一个小实验：把 max_steps 改小，确认运行停止；故意让最后的回答歪曲资料，确认当前验收确实抓不住。知道系统的盲区，比写一个看似严格的通过率更重要。

## 五、再接真实模型，但先不接真实动作

本练习可选支持本机 OpenAI-compatible chat completions 服务。只有已经准备好本地服务时再执行，不为了教程盲目下载模型或占用付费 GPU。

```bash
python3 agent.py --mode local --model "填写本机服务实际提供的模型名称" \
  --endpoint http://127.0.0.1:11434/v1/chat/completions \
  --question "ai-research-copilot 现在实现了什么，还没有实现什么？" \
  --output local-run-01.json
```

端口只是示例，必须匹配实际运行服务。接口格式、模型名称、JSON 遵从能力需要实测。本次没有运行真实模型，所以我不能先写“某个开源小模型完全够用”。

程序只接受 localhost、127.0.0.1、::1 的 HTTP 地址，拒绝重定向，不使用环境代理。它不携带密钥、不支持云服务鉴权。若未来要接云模型，应该单独实现经过确认的适配器、秘密管理与数据出站规则，不能简单解除限制把私人材料发出去。

我会准备十个固定问题：资料可回答的、资料没有答案的、含歧义的、要求调用不存在工具的、要求捏造引用的，各跑多次。记录正确性、合法动作比例、平均步骤、失败原因与耗时。只看 JSON 格式成功率是不够的。

模型成本也不能只算单价。真正要比较的是完成一次合格任务的成本，包括重试、浏览器耗时、服务费用和人工接管。小模型适合做哪些工作，应由这组任务的结果决定。

不要同时加入向量库、长记忆、MCP、调度和多 Agent。先让一个真实研究问题完成“读取允许的材料→给出引用→人工验收”。没有这个结果，更多组件只会让定位问题更难。

## 八、回到生活代理：我会怎样做第二个闭环

我会保留一个共享执行内核，用配置表达角色差异：职责、可用工具、可读资料、预算、需要确认的动作和失败后如何交还用户。多个 bot 不一定需要多个模型实例，更不需要彼此不停对话。

以聚餐助理为例，先用配套代码中的虚构数据做原型：

1. 输入人数、预算、区域、时间、饮食限制，缺必要条件时追问。
2. 只读搜索得到候选，明确数据是模拟，不能推断真实营业或空位。
3. 按硬条件过滤，给出候选及不能确认的部分。
4. 用户选择后，生成请求草稿：餐厅、日期、人数、预算、联系方式需求。
5. 展示明确确认界面。此时仍没有预约成功。
6. 模拟服务返回 reservation_id、失败或 uncertain，分别显示结果。
7. uncertain 时先查询订单，不能重复提交碰碰运气。

这七步是下一阶段验收规范，当前练习并未实现确认界面与预约服务。我会为它另外写 mock 服务，不把固定搜索输出冒充真实预订。

接真实电话或预订渠道之后，必须再解决地区覆盖、用户授权、费用、个人信息共享、取消规则、服务商回执和人工接管。电话拨通不等于订位成功；网页按钮点下去也不等于订单生成。

涉及副作用的动作需要稳定的 action_id、服务端确认记录和幂等键。确认至少绑定参数摘要、目标对象、金额范围及有效期；模型改了参数就必须重新判断授权。对外服务不支持幂等时，需要先查结果、人工处理不确定状态，不能假设数据库事务覆盖了外部世界。

### 云桌面帮我减少什么，又增加什么

统一操作系统、浏览器版本和工具环境，确实能减少执行环境差异。对没有 API 的网站，它也是一种入口。但云桌面没有消除登录过期、验证码、网站改版、支付确认和真实服务失败。

我不会先给每个 bot 分配一台永远在线的桌面。角色配置和执行环境是两件事。可以按用户与任务需要提供隔离会话，保留经过授权的必要状态，同时避免多个角色并发操作同一页面。是否持久化登录态，要有单独的安全设计。

有稳定、获授权的 API 时优先调用；只有确实需要网页操作时才启动浏览器或桌面，并让用户可以接管。这样的取舍能降低成本，也能把失败定位到具体渠道。

### 我的优势不能只写成“更便宜”

大公司的通用能力、数据和运维资源，我很难全面复制。可能有价值的方向是：一个明确人群的生活任务、更合适的默认设置、透明的费用与权限、可迁移的资料，以及一个地区真实可靠的服务渠道。但这些只是待验证假设。

我会用实际任务完成率、用户接管次数、一次成功任务总成本、重复使用意愿来决定是否继续。若用户只需要一个通用助手，而且现有产品已经足够好，我不该为了证明框架有用制造需求。

## 九、面试时，我当前可以怎样说

**问：你做过 Agent 吗？**

目前我的 ai-research-copilot 实现了研究问题 CRUD、Streamlit 页面和本地 JSON 存储，还没有生产 Agent。我准备在独立练习中手写只读循环，验证动作校验、工具执行、引用和失败路径，再迁移到项目服务层。现成练习由助手验证过，但我要自己跑过、改过，才把它作为我的实践经历。

**问：Agent 和普通工作流有什么区别？**

普通工作流由代码预先确定主要路径；Agent 把部分动作选择交给模型。两者都需要明确状态和边界。我会把授权、数据写入和任务验收留在确定性代码里，不把所有步骤都交给模型。

**问：RAG 和工具调用是什么关系？**

RAG 是检索相关材料辅助回答的一种方式；工具调用更广，可以检索、计算或执行操作。我的练习只有静态搜索与读取，不是向量检索系统。是否需要 embedding、重排和向量数据库，取决于资料规模与检索质量，不取决于是否叫 Agent。

**问：多角色怎么设计？**

先共享执行内核，用角色配置限定工具、上下文、预算和权限。只有独立子任务确有收益时才拆多个执行者。共享用户信息按授权范围提供，不让所有角色默认拿到所有私人资料。

**问：怎样避免无限循环和误操作？**

循环有步数、上下文、时间和费用边界。工具参数经过服务端验证，读写权限分开。外部写操作需要确认、幂等和结果核验。当前练习只有步数、字符预算及单次本地请求超时，没有完整生产调度和费用系统，我会明确这条边界。

**问：为什么不用框架？**

为了学习核心循环，我先写小版本；为了产品交付，我会按实际需求选成熟组件。手写与用框架不是立场问题，关键是我能解释依赖替我解决了什么，以及出问题时我是否能定位。

完成练习后，我再用自己的真实记录替换这里的计划描述：我修改了哪一处、触发了什么错误、如何修复、哪些测试仍不能证明可靠。没有测得的数据就不写百分比。

## 十、我照着走的顺序与停止条件

- **第一轮：跑通。** 不接模型，跑 14 项测试和 fake 示例，读懂每条 trace。产物：自己的运行记录。
- **第二轮：解释。** 关闭文章，从输入到 finish 讲一遍，解释两个失败测试。讲不清就先不扩功能。
- **第三轮：改一个边界。** 增加一个只读工具及测试，或改进答案与引用验收。不要同时重构所有模块。
- **第四轮：模型验证。** 本机服务可用后跑固定问题集，保留失败，不为演示挑最好的一次。
- **第五轮：回接项目。** 独立分支、隔离数据、只读服务适配，运行项目原测试与新增测试。
- **第六轮：生活模拟。** 做聚餐选择与确认的 mock 闭环。任务可用性不达标时，不接真实支付和电话。
- **第七轮：是否产品化。** 让少量目标用户尝试具体任务，再判断成本、可靠性和差异。不要把建设中台当成默认终点。

每轮我记录：日期、提交、实际执行命令、输出、失败、修复、未验证项。记录可以留在自己的学习分支；不要把本地运行文件、个人材料或密钥一并提交。
