## A1：如何设计服务数十亿用户的系统？

**问题背景：** 数十亿用户规模系统设计。

**考察能力（整理者判断）：** 将含糊规模转成负载模型；分离业务正确性与性能问题；从可验证的简单方案逐步演进，而不是报组件清单。

### 先问清什么

“用户”是累计注册、月活、日活还是同时在线？业务是账户查询、动态流、搜索还是转账？读写比例、请求峰值、数据保留期、地域分布、延迟目标是什么？哪些操作必须强一致？允许多大 RPO（可接受数据丢失窗口）和 RTO（恢复用时）？团队与预算是否支持跨地域运行？

### 回答主线

1. **先算数量级。** 假设 20 亿注册、2 亿日活，每日每活跃用户 50 次读取，则平均约 11.6 万读请求/秒；假设峰均比 5，峰值约 58 万/秒。这些都是演算条件，不是题目给出的事实。若每条响应 2 KB，单响应体流量约 1.16 GB/s，尚未计协议、重试、跨区与缓存命中。用户数本身不能推出机器数量。
2. **先画关键数据流。** 入口限流与鉴权，应用服务，读缓存与数据库，异步任务，观测与审计。划清同步关键路径和可异步动作，例如下单结果不能用“发了一个消息”代替已持久化的订单。
3. **再决定拆分。** 无状态应用方便扩容；数据按稳定业务键分区。选择用户 ID 分片需要解释跨用户查询、热点大户、扩容迁移、全局唯一 ID、跨分片事务与聚合查询。分片不是免费午餐。
4. **让一致性跟业务走。** 资料展示可容忍短暂陈旧；余额、库存扣减不能仅依赖缓存。为每类数据说明事实源、更新顺序、缓存失效和读己之写要求。全球部署还要区分主写地域、只读副本与跨区冲突处理。
5. **容量之外谈故障。** 单分区故障、缓存集体失效、重试风暴、下游超时、发布回滚都要有隔离、限流、退避与降级；降级不能突破授权或财务正确性。优先给出最小可运营方案，再说触发扩容的指标。

**面试官可能追问：** 分片数翻倍怎样迁移？一个明星账号导致热点怎么办？缓存宕机会否压垮主库？“99.99% 可用”如何定义测量窗口和失败分母？

**追问答题要点：**
- 分片扩容：先说明路由如何版本化，旧数据怎样回填与校验，迁移期间怎样承接增量，什么时候切读/切写以及如何回退；不能只说“一致性哈希自动解决”。迁移期双写必须处理部分成功，可用日志回放、版本和对账降低风险。
- 热点：先区分单键读热点与写热点。读热点可缓存、复制或请求合并；写热点不能无脑拆散破坏顺序/余额不变量，需要业务分解、排队或专属容量，明确吞吐上限。
- 缓存故障：限制回源并发、保护主库容量、按功能降级，冷启动逐步预热；增加重试可能让故障更严重。
- 可用性：例如按合格请求中满足正确性与延迟要求的比例计，明确维护期是否计入、客户端失败能否看到、区域/租户是否分别报告。不能用进程存活率代替用户成功率。

**常见失分：** 把注册用户当并发；看到亿级就必须微服务；只算 CPU 不算带宽、连接、索引与复制；用最终一致性解释所有业务；把缓存当唯一持久层。

**练习与岗位映射：** 用 Python 写容量表计算器，输入 DAU、行为次数、峰均比、载荷、留存、副本系数，做三种假设的敏感性分析。后端侧展示接口与分片边界；测试开发侧给热点、缓存失效与超时故障矩阵；AI 工程侧另算 token 吞吐、GPU 队列、长连接与租户预算，不能把 HTTP QPS 直接等同模型吞吐。此处方案为整理者设计练习，未做十亿级压测。

**一手参考：** [Google SRE：服务等级目标](https://sre.google/sre-book/service-level-objectives/) 用于进一步建立 SLI/SLO 语言；本题数值与架构均是上述假设推导，不是该资料的案例或容量承诺。

## A2：如何向千万设备推送消息？

**问题背景：** 千万设备消息推送。

**考察能力（整理者判断）：** 连接规模与消息吞吐拆分，在线/离线语义，流量扇出、设备状态、可靠性和用户可见结果。

### 回答主线

先确认“千万设备”是安装量还是同时在线；是广播、按人群还是单播；端是手机 App、浏览器还是可控 IoT；成功指平台接受、设备收到、应用处理还是用户读到；允许多长延迟，是否可过期或合并？

- **连接层与业务层分离。** 手机通常需要对接平台推送通道；可控设备可以讨论 MQTT/WebSocket 等长连接。自建连接网关需要设备鉴权、心跳、会话路由、断线重连和连接迁移。不要假设手机后台允许永久保活自己的连接。
- **先持久化消息/任务，再扇出。** 消息 ID、目标范围、版本、优先级、TTL 与状态单独建模。广播采用分批分区投递，限速与抖动重试，避免一次展开千万条请求压垮平台。用户与设备是一对多映射，token 可能失效，解绑和权限变更也要处理。
- **明确至少四种状态。** accepted、transport-delivered、application-acknowledged、read 不能混为一谈。可控客户端通过消息 ID、序列号与应用 ACK 补齐可观测性；平台不给回执的状态必须标未知。重要业务内容可保存在服务端收件箱，推送仅作“有更新”的提示，客户端恢复后按游标拉取。
- **容量估算。** 假设给 1000 万设备各发 1 条、要求 10 分钟内完成提交，平均至少 1.67 万次设备投递/秒；这还没有计失败重试和供应商配额。假设自建网关每连接占 10 KB，仅连接相关内存就约 100 GB，真实值必须压测，不能用该假设定机器数。
- **失效策略依业务。** 状态同步消息可合并为最新状态；支付事件不能无条件合并。离线长期不回来的设备不能保证“准时收到”，过期后应有明确状态与用户补偿流程。

**追问：** 广播与私信如何公平调度？相同设备重连到两个网关时谁拥有会话？一个用户 5 个设备如何去重？推送返回成功但用户没看到如何排查？

**追问答题要点：**
- 广播与私信：按租户/业务队列隔离并设置配额与优先级，重要私信留保底容量；优先级不能导致低优先级无限饥饿，应监控最老消息等待时间。
- 双网关会话：设备会话带递增 epoch 或租约，路由保存当前所有者；旧连接发送和 ACK 需要识别过期版本。只删除旧路由并不能阻止正在发送的旧进程。
- 多设备去重：先问业务是每人一次还是每设备一次。消息事件ID可相同，但投递状态按设备记录；“某设备已读”是否影响其他设备是产品语义。
- 返回成功但未到达：沿消息ID检查平台接受、token有效性、TTL、客户端在线与权限、应用回执。没有终端证据的区段写未知，不从服务端200反推设备问题。

**常见失分：** 推送 API 的 200 等同用户收到；平台离线缓存等同永久消息库；一条业务事件一个无界重试循环；忽略退出登录后信息误推。

**练习与岗位映射：** 做 1000 个模拟客户端的协议级练习，注入丢 ACK、重复投递、重连、token 失效与慢消费者；分别统计提交延迟、终端 ACK 延迟、超时/未知比例。测试开发重点是状态证据链，不只看接口返回码；AI 工程可类比长耗时生成任务的完成通知，但不能用通知代替结果持久化。

**已核验依据：** [FCM 消息生命周期](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-lifespan) 明确区分接受投递与设备实际送达，也说明离线、TTL 与消息合并影响。它支撑边界说明，不意味着所有平台行为一致；平台限制需按实际通道重新核验。

## A3：消息中间件如何做到“不重、不丢”？

先用[网络N6](networking-and-protocols.md#n6)区分TCP确认与业务结果，再展开本节跨组件故障边界。

**问题背景：** 消息可靠性与重复问题。

**考察能力（整理者判断）：** 识别端到端保证范围、超时的不确定性、持久化与确认顺序，能用故障点分析证明设计。

### 回答主线

先定义“不丢”：从业务事务提交、生产端收到 ACK，还是用户点发送开始？定义“不重”：网络不重传、消费者只取一次，还是业务状态只改变一次？这些不是同一个目标。

1. **生产端：** 本地业务写数据库后再发消息，存在“提交成功但尚未发送就崩溃”的窗口；先发消息也有业务回滚窗口。可设计事务 outbox，将业务变更与待发布事件放同一数据库事务，再由发布器重试。outbox 仍会重复发布，不能因此宣布全链路 exactly-once。
2. **broker：** 验证持久化、复制、确认策略、保留期、故障切换和允许的灾难模型。ACK 超时表示结果未知，可能已保存；重试必须能容忍。磁盘与副本同时不可恢复、保留期已过等边界不能被“不丢”口号抹去。
3. **消费者：** 业务处理前提交位点可能丢业务效果；处理后提交位点会在中间崩溃时重做。因此常用至少一次投递，加以业务键去重。把去重记录与业务更新放同一事务，并依赖唯一约束或条件更新处理并发，不能“先查有没有，再无锁执行”。
4. **外部副作用：** 扣款、发邮件、调用模型服务不自动加入本地数据库事务。优先使用对方支持的幂等键与结果查询；无法查询的超时结果进入待核查，不盲目重复支付。幂等键的业务范围、有效期、重放窗口和请求参数冲突必须定义。
5. **有范围的 exactly-once：** Kafka 事务可原子关联 Kafka 输出和消费位点；读取隔离、事务配置与故障条件也必须满足。写任意外部数据库或第三方 API 需要额外协作，不是打开一个开关就成立。[Kafka 4.1 消息语义与事务设计](https://kafka.apache.org/41/design/design/)

**具体故障推演：** “消费者已给账户加 100，提交 ACK 前崩溃”时重投同一 event_id。如果去重插入和加余额同一事务，第二次唯一键冲突被识别为已处理，并取回原结果；如果先写去重再单独加余额，两步中间崩溃会永久漏加。能指出这个窗口比背三种投递语义更重要。

**追问：** 去重表何时清理？顺序与幂等是不是一回事？毒消息如何隔离？重平衡期间旧消费者还在处理如何阻止重复副作用？

**追问答题要点：**
- 去重保留期：至少覆盖可能发生的重投、补偿与历史重放窗口；若允许多年回放，短TTL去重不够。也可用长期业务唯一键保护核心效果，但存储成本与键复用规则要说清。
- 顺序与幂等：幂等防同一事件重复效果，不防新旧不同事件乱序覆盖；可按实体分区并用业务版本条件更新，解释版本跳号/缺失事件如何补齐。
- 毒消息：有限重试、错误分类、隔离并告警，保存原消息和失败证据，修复后受控重放；死信只是可追踪待办，不是业务完成。
- 重平衡：旧消费者可能还在执行，提交位点被拒也不能撤销已发生副作用。需要业务幂等、所有权版本或下游支持的fencing，而非只依赖消费者组。

**常见失分：** “ACK+持久化就绝对不丢”；把 broker 去重当业务幂等；把死信队列当成功处理；重试次数耗尽后不记录待处理任务。

**练习与岗位映射：** 画出生产、确认、业务提交、位点提交四个边界，逐点杀进程，核对业务总量不变量。Python 后端实现唯一业务键；测试开发验证失败恢复；AI 工程用同一任务 ID 去重结果提交，同时承认模型调用可能重复产生费用，结果幂等不等于调用成本只发生一次。此设计未在本次运行 broker 实测。

## A4：从输入 URL 到页面显示，发生了什么？

**问题背景：** URL 到页面的端到端过程。

**考察能力（整理者判断）：** 跨层定位，不把网络、服务器与渲染混成固定流水线。

### 口述主线

先说明以下是一次典型 HTTPS 顶层导航，实际会受缓存、连接复用、Service Worker、重定向和 HTTP 版本影响：

1. 浏览器解析 URL 并执行导航相关安全与缓存判断；需要时解析域名。已有缓存与连接可省去部分网络步骤。
2. 建立或复用连接。HTTP/1.1、HTTP/2 常见于 TCP 上配合 TLS；HTTP/3 使用 QUIC，不能说所有 HTTP 都先 TCP 三次握手。
3. 请求经过网络与服务端入口，路由、鉴权、业务处理、缓存或数据库查询，再返回响应；可能继续重定向，或在缓存有效时不访问源站。
4. 浏览器解析 HTML、发现资源，构建 DOM；解析 CSS 并计算样式；执行脚本可能改变 DOM、引入资源或占住主线程。之后进行布局、绘制和合成。资源请求、解析与执行有交错，并非全部串行。
5. 首屏可见、DOM 完成、load 触发、可交互以及用户真正完成任务不是同一个时间点。单页应用的路由变化也未必触发完整网络导航。

以上浏览器流程参考 [MDN 浏览器工作原理](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/How_browsers_work)，HTTP/3 传输差异参考 [RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html)。

### 面试官希望你能定位，而不仅背流程

假设用户说“页面白屏 5 秒”：先看网络瀑布，区分 DNS/连接/首字节/下载耗时；TTFB 高也不能直接归因 SQL，可能入口排队或上游等待。若资源已返回，检查主线程长任务、脚本异常、渲染阻塞资源与接口依赖。使用请求 ID 串起客户端、网关和 Python 服务 trace。测试中比较冷/热缓存、弱网、错误响应和不同协议，而不是只做本机秒开截图。

**追问：** 缓存命中时哪些步骤不会发生？304 和本地直接命中有何区别？为何后端耗时 50 ms 但用户等 3 秒？TLS 复用对延迟有什么影响？

**追问答题要点：**
- 缓存命中：新鲜本地缓存可省掉资源网络往返；协商缓存仍发请求并可能收到304，通常复用已有响应体。区分顶层文档与每个子资源的缓存，不说“页面命中所以完全没网络”。
- 50ms对3秒：先核对计时范围与时钟，补查连接池/入口排队、DNS与连接、资源依赖、重试、下载和主线程；服务端日志往往只覆盖中间一段。
- 连接/TLS复用：已有合格连接可免新建开销；连接是否可复用受目标、协议、状态等约束。不要承诺每次固定省几个RTT，握手版本和恢复方式会不同。
- 指标选择：导航完成并不代表流式AI回答结束；可分别观察首字节、首内容、可交互与用户任务完成，用同一请求/会话标识关联证据。

**常见失分：** HTTP 必然新建 TCP；DNS 必然查遍所有层；HTML 下载完才发现任何资源；load 等于用户体验良好；混淆服务端渲染和浏览器渲染。

**练习与岗位映射：** 用浏览器开发者工具记录同一页面冷、热两次瀑布，给每一段延迟找证据。Python 后端重点是排队、连接池和依赖调用；测试开发重点是跨端观测与错误注入；AI 网页还应拆开首 token、生成完成、流式渲染三个指标。此处只给练习，不声称已完成网页测量。

## A5：InnoDB 的 B+ 树到底能存多少行？

**问题背景：** InnoDB B+ 树容量估算。

**考察能力（整理者判断）：** 理解页、索引记录、扇出与高度，并能解释为什么“3 层存 2000 万”不是定律。

### 回答主线与可核算例子

先澄清是聚簇索引还是二级索引、页大小、键长度、平均行记录长度、填充率以及“3 层”是否包括根和叶。普通 InnoDB 索引页默认 16 KB，但可配置；实际记录开销、页内空间和插入方式会改变容量。[MySQL 8.4 索引物理结构](https://dev.mysql.com/doc/refman/8.4/en/innodb-physical-structure.html)

使用简化模型：叶子每页容纳 L 条记录，非叶子平均扇出 F，根到叶共有 H 层，则行数数量级为 L × F^(H−1)。这是满度简化，不是页格式精确计算。

**假设例子：** 页 16,384 B，可用空间按 14,000 B；非叶子索引项平均 20 B，则 F≈700；聚簇叶子平均一条完整页内记录 1,000 B，则 L≈14；3 层约为 14×700²=6,860,000 行。如果页内记录变成 200 B，L≈70，相同假设就变成约 3430 万行。20 B 与 14,000 B 只是人为建模参数，不是 MySQL 固定指针/页头规格。

聚簇索引叶子承载行数据；二级索引还包含主键，用它回查聚簇索引可能多走一次树。长主键会影响二级索引体积，因此不能只把业务字段宽度代入。变长字段与行外存储也使“平均整行字节数”不一定等于页内记录大小。[MySQL 8.4 聚簇与二级索引](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)

高度也不等于每次必然进行同次数量的磁盘 I/O，热页在 buffer pool 中可能命中；并发、回表、范围扫描和预读都会影响实际表现。

**追问：** UUID 与短整型主键如何改变二级索引？树高没增加为什么查询变慢？覆盖索引是否任何场景都不回表？随机插入为什么可能降低空间利用率？

**追问答题要点：**
- 长主键：会增大聚簇内部键和二级记录的主键负担；随机值还可能影响局部性。不能只以UUID字符串长度判断，要确认存储编码和实际插入顺序。
- 高度未变仍慢：数据工作集超过buffer pool、扫描范围扩大、回表增多、锁等待、缓存命中变化都可能发生；用计划和运行指标区分，而不是归因“树坏了”。
- 覆盖索引：逻辑上所需列齐全可能省回表，但MVCC可见性等情况仍可能需要聚簇记录；先限定执行与并发场景，不用“永不回表”措辞。
- 随机插入：页分裂和不同填充程度影响空间与局部性；不能用单个固定填充率预测所有表，需用真实插入分布验证。

**常见失分：** 背固定行数；把非叶节点都当完整行；忽略主键附加成本；把页数、行数、树高混用。

**练习与岗位映射：** 做键宽/页内行宽/填充率三维敏感性表，再在隔离 MySQL 测试库逐步插入不同长度记录，用实际统计和查询计划比较数量级。不要声称估算就是内部精确页数。AI 元数据表若有大文本/向量字段，先分清页内表示与外部存储；测试开发可验证数据增长后的计划回归。本次只核算简化模型，未启动 MySQL 验证。

## A6：如何设计财务对账系统？

**问题背景：** 财务对账系统设计。

**考察能力（整理者判断）：** 业务口径、不可变证据、数据差异分类、可重跑与审计，比单纯“大表 join”重要。

### 回答主线

1. **界定双方账本。** 是订单与支付流水、支付渠道与内部账，还是清算入账与银行账？对账周期、结算日/交易日、时区、币种、手续费、退款、冲正和分账规则由谁定义？不能未经确认把跨日未达账判为错账。
2. **保留原始输入。** 每批原始账单保存来源、下载时间、业务覆盖范围、校验信息、格式版本和导入批次。原始证据不可被“清洗结果”覆盖；对账重跑应固定输入版本与规则版本。
3. **标准化但不丢语义。** 金额用整数最小货币单位或明确精度十进制，不用二进制浮点凑差；币种必须显式。不同币种的小数位不一定相同。外部交易号、内部订单号、退款号等构成可追溯匹配链，不能只用金额+时间做唯一匹配。
4. **分层匹配。** 先批次总额、笔数等控制汇总，再明细匹配；总额相等不代表笔笔正确。对正常匹配、单边、金额不符、状态不符、重复、跨日待达分别归类。部分退款/一对多结算要按业务规则聚合，不能默认一行对一行。
5. **差异闭环。** 输出差异工单和证据，设置待观察窗口、负责人、复核与处置结果。对账服务负责发现和解释差异，不应悄悄改账“抹平”。如需更正，使用有权限、审计和审批的独立流程。
6. **可靠重跑。** 批次幂等、断点恢复、迟到数据补跑、输出版本化。财务截止时刻与工程任务结束时刻不同。涉及个人/交易数据时限制访问和日志暴露。

**小例子：** 内部支付 100 元、退款 30 元、渠道收取 1 元费，若外部账单是净清算 69 元，直接拿 100 和 69 对比会误报。必须先确认该账单是毛额、净额还是分列字段，且费率与费用所属期由真实业务规则决定；这不是任何渠道的实际计费规则。

**追问：** 两边汇总相等但明细差异怎么办？晚到三天的退款如何重算且不覆盖历史报告？同一渠道号重复出现怎么判断？如何证明输入没有漏文件？

**追问答题要点：**
- 汇总相等但明细不同：相反方向差额可能互相抵消，仍逐笔分类；控制总额只是快速校验，不替代明细证据。
- 迟到退款：对受影响业务期产生新版本结果，保留原截止时点所知事实；不要静默重写已确认报告。是否跨期调整由实际财务规则与授权人员决定。
- 重复渠道号：先判断渠道号的唯一性范围，例如渠道、商户、交易类型；原始记录均保留，再按规则识别重传、冲正或真重复，不能直接去重丢证据。
- 漏文件：维护预期批次清单、文件序号/覆盖区间、导入清单与笔数/金额控制，核对缺口并告警；“导入成功”只能证明拿到的文件被处理，不能证明文件已齐。

**常见失分：** 自动用差额冲平；浮点金额；只看总额；重复跑生成重复工单；没有业务规则版本。

**练习与岗位映射：** 使用虚构 CSV 构造漏单、重复、部分退款、时区跨日与手续费场景；实现确定性匹配并生成“证据→差异类别→待办”，测试重跑不重复生成有效差异。Python 后端体现数据建模，测试开发体现规则覆盖；AI 可以辅助解释差异，但确定性对账与授权改账不能由模型自由生成替代。

**一手参考：** [Python 3.12 decimal](https://docs.python.org/3.12/library/decimal.html) 支撑十进制表示与显式舍入；对账流程是整理者的工程设计，不是会计合规意见或某机构制度。

## B1：接雨水，如何解释算法正确性？

**问题背景：** 接雨水算法。

**考察能力（整理者判断）：** 建模、边界、循环不变量、复杂度、验证策略，而不只是刷题记忆。

### 回答主线

先确认输入是非负整数高度、每根柱子宽度为 1、是一维截面，不是二维地形。位置 i 的水量等于 `min(左侧含自身最高柱, 右侧含自身最高柱) − height[i]`。这给出容易检查的基线解：逐点扫描两侧 O(n²)；或预存前后缀最大值，O(n) 时间、O(n) 额外空间。

再优化到双指针。维护已经扫描的左、右最大值，始终结算较低最大值的一侧：另一侧已经存在不低于它的边界，因此当前较低边界足以决定该位置的水；如果当前柱子更高，则先更新该侧最大值，该位置贡献为 0。每次只移动一个端点，每根柱子只处理一次，故时间 O(n)、额外空间 O(1)。初始两侧最大值均为 0；空数组直接不进循环。不要只说“两边夹逼”却解释不了何时能安全结算。

```python
def trap(height: list[int]) -> int:
    left, right = 0, len(height) - 1
    left_max = right_max = 0
    volume = 0
    while left <= right:
        if left_max <= right_max:
            left_max = max(left_max, height[left])
            volume += left_max - height[left]
            left += 1
        else:
            right_max = max(right_max, height[right])
            volume += right_max - height[right]
            right -= 1
    return volume
```

**契约：** 上面没有做输入类型/负值校验，假定题目保证非负整数列表；生产 API 应在边界层验证，而不是让调用方误以为负高度有已定义含义。Python 整数不会像固定宽度整型那样溢出，但输入长度仍受内存和时间约束。

**追问：** 能否用单调栈？柱宽不同怎么办？流式输入只有左侧信息能否立即给精确总量？二维积水为什么不是直接套这段双指针？

**追问答题要点：**
- 单调栈：维护尚未确定右边界的柱下标，遇更高柱时弹出盆底，以两边较低高度和跨度计算新增水层；需避免对同一层重复计数，时间O(n)、空间最坏O(n)。
- 不同柱宽：逐位置前后缀高度公式仍可乘该位置宽度，双指针也可据此扩展；必须先定义坐标与宽度，不能继续把跨度当下标差。
- 流式输入：未知右边界时通常不能立即确定精确总量；可保留未闭合状态，或允许结束时再输出。输出早期猜测不是精确在线算法。
- 二维：水可能从多个方向逃走，左右边界不够；需要边界优先扩张等不同建模。能解释为什么当前不变量失效，比硬套一维代码重要。

**常见失分：** 用平均高度；更新最大值的顺序不一致导致负贡献；忽略 0/1/2 根柱子；只测经典例子；声称双指针可直接解决二维问题。

**实践结果：** [完整实现与可复跑测试](../practice/trapping_rainwater.py) 在 Python 3.12.14 实际运行通过：9 个具名案例、长度 0—7 且每项取 0—3 的 21,845 个穷举数组、固定种子 1,000 个随机数组。用独立 O(n²) oracle 对拍，并验证反转不变、统一加高不变、等比例放大水量同比变化。详见 [测试记录](../practice/trapping-rainwater-test-report.md)。有限测试不能替代正确性证明；没有把其他设计题写成已实测。

**岗位映射：** 后端面试重视正确性与复杂度；测试开发可用这题展示 oracle、边界与变形测试；AI 工程可演示审查模型生成算法时如何拒绝“样例过了就正确”。

## B2：MySQL 的 ACID 与 MVCC、redo、undo 如何对应？

**问题背景：** 结合 InnoDB 机制解释事务特性。

**考察能力（整理者判断）：** 用并发与崩溃例子解释机制，不机械地把每个字母配一个文件。

### 回答主线（MySQL 8.4 / InnoDB）

- **A，原子性：** 一组数据库修改整体生效或撤销；undo 提供撤销修改所需信息。不要把“多个外部服务调用”自动视为一个 InnoDB 事务。
- **C，一致性：** 事务应使数据满足定义好的不变量，数据库约束与应用逻辑共同负责。数据库无法自动知道“同一订单只能扣一次款”或余额的全部业务规则，除非正确建模并执行。它也不同于分布式系统所说的副本线性一致性。
- **I，隔离性：** 不同隔离级别允许的并发可见性不同，InnoDB 结合锁与 MVCC。普通一致性读与锁定读不能混为一谈；MVCC 不是“任何读写都不加锁”。
- **D，持久性：** 提交后的恢复依赖日志刷盘、存储和配置保证；redo 用于崩溃恢复，脏页可晚于日志写回。不同刷盘配置改变故障下的丢失风险，不能只说“有 redo 就永不丢”。[ACID 模型](https://dev.mysql.com/doc/refman/8.4/en/mysql-acid.html)、[redo](https://dev.mysql.com/doc/refman/8.4/en/innodb-redo-log.html)、[刷盘参数](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html#sysvar_innodb_flush_log_at_trx_commit)

**MVCC 如何得到旧版本：** 聚簇记录的事务信息和回滚指针配合 undo，使一致性读重建所需历史版本；undo 同时参与回滚，不只是“旧数据备份”。版本不是复制一份完整表。长事务会使还可能被读到的历史版本不能及时清理。[多版本机制](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)、[undo](https://dev.mysql.com/doc/refman/8.4/en/innodb-undo-logs.html)

**快照例子：** T1 在 RR 下首次普通一致性查询看到余额 100；T2 改为 80 并提交；T1 再作普通一致性读仍按原快照读，RC 则为每次一致性读建立新快照。事务自身写入和锁定读有另外语义，不能把这例子外推成“RR 下任何语句都永远只看第一次的内容”。[一致性读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

**避免资金并发错误：** “读余额→Python 计算→写回”可能被另一个请求覆盖。视业务可采用条件更新、版本号 CAS 或锁定读加同一事务，并检查受影响行数与死锁重试。数据库事务能保护它管理的数据；调用第三方支付还要考虑 A3 的幂等和结果未知。[锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

**追问：** redo 和 binlog 有何作用边界？为何 RR 下 UPDATE 和之前 SELECT 看起来不同？长事务对清理和存储有什么影响？为何进程崩溃与整机断电不是完全一样的测试？

**追问答题要点：**
- redo/binlog：redo服务InnoDB恢复，[binlog](https://dev.mysql.com/doc/refman/8.4/en/binary-log.html)面向服务器层变更记录及复制/恢复用途，两者不能互换；若要展开提交协作，要说明崩溃位置与两者刷盘设置，不能画“先写A后写B”就宣布原子性。
- RR读与修改：普通一致性读按快照，而修改/锁定语句有不同可见性和锁语义；先给明确两连接时序，避免用“可重复读”推导所有语句读同一历史版本。
- 长事务：长期保留快照可能阻碍版本清理，增加历史链和空间压力；缩短事务需确认业务边界，不能为了性能随意拆掉本应原子的操作。
- 崩溃测试：进程终止、OS崩溃、断电可能丢失的缓存层不同；记录配置和存储保证，区分未确认与已确认事务，不用一次kill实验推出断电也安全。

**常见失分：** ACID 的 C 等于 CAP 的 C；undo 只存在内存；redo 是完整 SQL 回放；MVCC 完全替代锁；把 RPC 超时当事务一定回滚。

**练习与岗位映射：** 两个独立连接分别在 RC、RR 下复现读差异与并发扣减，记录每个 BEGIN/SELECT/UPDATE/COMMIT 的时序、隔离级别、返回值。Python 注意连接池复用事务与异常回滚；测试开发保存可复现时序；AI 工程将模型任务状态与结果引用原子提交，但不宣称外部推理调用也包含在事务内。本次未运行 MySQL 实验。

## B3：一条 SQL 从提交到返回，经过哪些阶段？

**问题背景：** SQL 请求完整链路。

**考察能力（整理者判断）：** 区分客户端等待、服务端规划和引擎执行，解释“同样 SQL 为什么今天变慢”。

### 回答主线（以 MySQL 8.4 普通 SELECT 为例）

先说明连接可能早已在池中建立，事务和会话状态仍影响查询。应用等待连接、序列化参数与网络发送之后，服务端进行语法/语义及权限等检查，优化器决定访问路径、连接顺序和算子，执行器与 InnoDB 配合读取索引/数据，应用过滤、连接、排序或聚合，再通过协议返回。具体检查与优化不必强行背成永不变化的内部函数序列。

InnoDB 从 buffer pool 或存储读取页面；根据语句和事务语义进行可见性判断或加锁。索引命中也可能扫描大量记录、回表、排序，不能把“用了索引”当快速的充分条件。MySQL 8.4 不能套用旧版“先查服务器 Query Cache”的流程；旧查询缓存已经移除，见[官方历史版本说明](https://docs.oracle.com/cd/E17952_01/mysql-5.7-en/query-cache.html)。

**验证计划而非猜测：** EXPLAIN 看估计路径；EXPLAIN ANALYZE 能提供实际执行信息，但会执行查询，应只在安全的测试或受控只读范围使用，重查询也有资源代价。比较估计行数与实际行数，可以定位统计信息偏差；再看扫描/返回比、索引选择、排序与临时结果。[MySQL 8.4 执行计划](https://dev.mysql.com/doc/refman/8.4/en/execution-plan-information.html)

**一个面试场景：** `WHERE tenant_id=? AND created_at>=? ORDER BY created_at LIMIT 50`。先问租户大小是否倾斜、时间范围是否大、返回哪些列，再评估复合索引，而不是给所有列各加一个单列索引。选索引还需平衡写放大、存储与维护成本；测试不同参数和冷热缓存，不能用一个小租户的结果证明所有租户快。

### 返回阶段同样重要

服务端完成不代表用户拿完结果：大结果集的网络传输、驱动缓冲、Python 对象创建、ORM N+1 和 JSON 编码均可占时间。长时间持有游标/事务还可能拖累资源回收。应将“连接池等待、数据库执行、结果读取、应用处理”分开打点，而不把一个总耗时都叫 SQL 慢。

**追问：** 为什么优化器不选你新建的索引？预编译是否消除 SQL 的全部开销？分页偏移很大为何变慢？查询日志很快但接口很慢如何查？

**追问答题要点：**
- 不选新索引：可能选择性差、回表成本高、统计信息不准或排序代价更高；先比较估计和实际，不能直接强制索引。提示只可作为受控验证，不是长期自动修复。
- 预编译：参数化有安全和复用解析等价值，但不消灭锁、IO、执行、网络及结果构造开销；具体缓存/重新优化行为要按版本和驱动确认。
- 深分页：大OFFSET通常仍需定位/跳过前面的结果；稳定排序下可评估基于游标的续查，注意排序键唯一性与并发新增删除造成的边界变化。
- 接口慢数据库快：查连接池等待、N+1次数、结果传输/解码、ORM对象及后续依赖；不能只拿一条SQL的耗时对比整个接口。

**常见失分：** 只背解析器/优化器名词；WHERE 写的先后顺序就是执行先后；认为命中缓存等于零成本；忽略返回阶段；在生产无边界执行 ANALYZE。

**练习与岗位映射：** 使用假数据构造租户偏斜，记录计划、结果行数与应用端阶段耗时；同时比较批量查询与 ORM N+1。后端侧解释访问模式，测试开发建立计划/延迟回归样本，AI 工程检查检索前后元数据查询与批处理。此处未执行真实数据库压测。

## B4：Raft 怎样保证一致性，又不能保证什么？

**问题背景：** Raft 一致性机制。

**考察能力（整理者判断）：** 说清安全性、可用性与读语义，不把“选主+多数票”当完整答案。

### 最小正确回答

Raft 用于复制状态机的日志一致性，面向崩溃/恢复等非拜占庭故障，不防恶意节点伪造协议。固定 N 节点需要多数 `floor(N/2)+1` 才能推进；失去多数可以停止写入而保持安全，活性还依赖网络与节点最终能及时通信。

任期和每任期投票约束防止同任期多主；选举比较候选人最后日志的任期与索引。AppendEntries 的前序日志匹配约束处理分歧。leader 通过多数副本直接确认的是**当前任期**条目，不能笼统地说旧任期条目一过半就提交；当前任期条目提交时，前面的条目可随之被间接提交。提交与应用到状态机是不同阶段。

只向“自认为是 leader”的节点读不保证线性一致：旧主可能已被隔离。正确读路径需要确认当前领导权、已提交边界以及本地状态机已应用到相应位置；lease 读还依赖时钟等额外假设。客户端重试也需要请求去重，日志一致性不自动等于业务请求仅执行一次。依据：[Raft 作者扩展论文，§5、§8](https://raft.github.io/raft.pdf)。

### 用故障例子展示理解

画 5 个节点，隔离成 2+3：少数侧即使旧 leader 尚未意识到失联，也不能继续提交新写；多数侧能在满足选举条件后推进。客户端对旧主的写超时，应视为结果未知并用请求 ID 查询/重试，而不是自行断言“肯定没写成功”。

然后给出三个不同断言并要求自己逐个验证：

- 某条日志已写到一个节点磁盘。
- 某条日志已经提交。
- 某个节点的状态机已经应用该日志，可以用它回答读请求。

前者不推出后者。这个区分也能解释为什么 follower 本地读取可能陈旧，以及为什么快照、日志压缩与成员变更不能随意实现。

**追问：** 3 节点与 4 节点各能容忍多少不可用节点？网络恢复后未提交分支如何处理？选举日志新旧为何不是只比长度？本地磁盘丢了持久化投票状态意味着什么？成员变更为什么不能直接改数组？

**追问答题要点：**
- 节点数：固定3节点多数为2，4节点多数为3，均只能在丢1节点后仍有多数；加一节点不一定增加故障容忍度，还要考虑故障域是否独立。
- 未提交分支：网络恢复不意味着所有曾收到的写都必须保留；客户端对超时请求要查证或幂等重试，不能从“曾写本地日志”推导业务已提交。
- 比日志新旧：只比较长度会误把较旧任期的长分支当成更新；要同时考虑任期与索引，具体反例用论文选举规则逐步演算。
- 持久状态/成员变更：丢失投票约束或随意变更投票集合会破坏证明所依赖的条件；使用成熟实现并核验恢复、加入/移除流程，不把数组增删当安全重配置。

**常见失分：** Raft 是拜占庭容错；任何多数复制即提交；leader 读天然线性一致；多数节点存活就绝对可用；把复制日志当业务去重功能。

**练习与岗位映射：** 手工画 5 节点的 term/index/commit/applied 时间线，再在学习用模拟器验证分区与恢复；测试开发应区分安全性断言（不出现冲突已提交值）与恢复后活性断言。Python/AI 后端通常应正确使用已成熟的一致性存储，而非为面试临时手写生产 Raft。本次未实现或验证 Raft 集群。

## B5：Hive 的原理是什么？

**问题背景：** Hive 实现原理。

**考察能力（整理者判断）：** 区分 SQL 编译、元数据、执行引擎与底层存储，知道分析型系统与在线数据库的边界。

### 回答主线与版本边界

这里以 **Hive 4.0 系列** 的基本概念为基线，不声称是最新版本。Hive 接收 HiveQL，借助元数据解析表与列，将查询转换和优化为执行计划，再交给执行引擎运行。Metastore 保存 schema、分区等元数据，不等于把全部业务行数据存进 Metastore 的关系数据库。[Hive 官方架构设计](https://hive.apache.org/development/designdocs/design/)

旧材料常把 Hive 简化为“SQL 转 MapReduce”；面试应主动指出这是历史概括。采用 Tez 时，查询可以表达为任务 DAG，不能说每条 SQL 都固定映射成一个 MapReduce 作业。[Hive on Tez 设计](https://hive.apache.org/development/designdocs/hive-on-tez/)

从一个按日期统计租户事件的查询出发：分区过滤减少待读范围；列式文件可以减少无关列读取；统计信息与优化器影响连接计划；shuffle、数据倾斜与小文件会左右实际成本。并非写了分区字段就自动裁剪成功，必须看计划与实际扫描指标。Hive 也不能简单说“不支持事务”：4.0 官方说明列有 ACID 与 compaction 的改进；是否能使用某能力取决于表类型、格式和配置。[Hive 4.0 主要变化](https://hive.apache.org/docs/latest/overview-of-major-changes/)

### 进一步解释权衡

在线点查关注低延迟、单行读写；离线分析更关注大范围扫描、聚合和吞吐。不能因为“底层能存数据”就把 Hive 当每次 API 请求的默认主库。也不要把 Hive、HDFS、Tez、Spark、Iceberg 叫成同一个东西：存储系统、执行引擎、表格式、SQL 层和目录服务有不同边界；实际部署的兼容性要看版本矩阵。

**追问：** 分区和分桶的目的分别是什么？为什么一天一个分区仍有海量小文件？Join 一侧极度倾斜如何定位？Metastore 可用但查询失败可能在哪里？更新表后为何要关心 compaction？

**追问答题要点：**
- 分区/分桶：分区按数据组织和条件减少读取范围；分桶按指定规则拆分数据，目的与优化机会不同。不能笼统说任意WHERE都能用分桶跳过数据。
- 小文件：频繁小批写入与并行任务过多可能产生大量文件，导致规划、文件打开与调度开销；评估合并和批量大小，但保留更新/并发语义。
- 倾斜：检查任务耗时分布与热点键，不只看平均耗时；可讨论热点单独处理、预聚合或改变连接策略，盐值方案必须保证聚合/去盐后结果正确。
- 元数据可用但查询失败：执行资源、权限、实际数据文件、格式兼容和网络仍可能出错；compaction也有资源与后台维护成本，事务支持不等于无需运维。

**常见失分：** Hive 就是 HDFS；元数据就是全部数据；所有版本只支持 MapReduce；支持 SQL 就应承担 OLTP；没有计划和扫描量证据就说“加分区一定快”。

**练习与岗位映射：** 先用样例数据设计“按日、按租户”的分析表，对比扫描全表与日期过滤的计划，讨论高基数分区是否导致管理成本。Python 后端学习批处理接口与数据质量；测试开发检验重复、迟到、schema 演进；AI 工程用于训练/评估数据加工时还要保存数据版本、划分和泄漏检查。这里只提供练习设计，没有启动 Hive 或完成性能对比。

## B6：秒级精度、最长两年、不能丢的延时队列怎样设计？

**问题背景：** 长周期延时任务系统。

**考察能力（整理者判断）：** 从调度算法推进到持久化、时钟、故障恢复与业务效果保证，识别不可能无条件兑现的绝对措辞。

### 先明确保证

“秒级”指不早于计划时间、99% 在一秒内被领取、开始执行还是执行完成？全机房不可用时仍必须准时吗？“不丢”从接口成功响应开始算吗？任务量、每秒到期量、载荷大小、可取消/改期、租户隔离与恢复目标是什么？两年后用户身份、业务规则、执行代码都可能变，需要任务 schema 版本与授权再校验。

### 一个可解释的设计

1. **持久化事实源。** 接受任务前在可靠存储写入 task_id、due_at_utc、payload_ref、版本、状态、重试信息和创建证据，成功响应绑定明确持久化条件。远期任务按时间区间与散列分区组织，建立状态/到期索引；不能把两年的任务仅放内存时间轮。
2. **冷热分层。** 长期任务保留在持久层；扫描器把近期窗口任务加入短期优先队列或时间轮。内存层仅是加速层，重启能从事实源重建。提前入队并不意味着提前执行，执行前再次检查到期和当前任务版本。
3. **避免迁移丢失。** 任务由持久层送往 ready queue 时，直接“先删除再发送”会丢，“先发送再删除”会重复。可使用同事务 outbox 或保留可重扫状态，允许重复投递，再由领取/执行阶段去重。方案须明确清扫与补偿路径。
4. **领取、租约与重试。** 工作者原子领取 pending 任务并保存 attempt/version/lease_until；失败或过期租约可重新领取。旧工作者可能在租约过期后继续执行，必须有 fencing token/版本校验及下游幂等，不是拿到分布式锁就万事大吉。成功结果和完成状态尽量同事务保存；外部副作用沿用 A3 的结果未知处理。
5. **时钟与迟到。** 计划时刻用 UTC 时间保存；进程内等待间隔用单调时钟辅助，不能把单调时钟读数当跨重启的绝对截止时间。监控系统时钟跳变、偏差和调度滞后。恢复后扫描逾期未完成任务，按照“补执行/过期作废/人工核查”的业务策略处理，不能静默丢弃。[Python 时钟语义](https://docs.python.org/3/library/time.html#time.monotonic)
6. **容量与可观测性。** 秒级调度需要预算扫描、领取、排队、执行启动的总延迟。即使扫描周期 1 秒，也不保证全部任务 1 秒启动。突发百万任务同秒到期时，需要分片、容量预留、限流和清楚的优先级；持续跟踪 oldest_due_lag、逾期数量、重试、死信/待人工、恢复耗时。

**举例说明失败边界：** 任务到期时机房失联 5 分钟，系统不能同时保证“严格准时”和“不可用时不运行”。能承诺的是在定义故障模型与持久化条件下不静默丢任务，恢复后可核查和补执行；这不等于任何灾难下绝对不丢，更不等于外部效果恰好一次。

**追问：** 用户到期前一毫秒取消怎么办？两个调度器同时捞到同一行怎么办？数据库与 ready queue 中间崩溃怎样恢复？操作系统时间回拨十分钟如何处理？两年前的 payload 新版程序还读得懂吗？

**追问答题要点：**
- 临界取消：定义取消生效点，用状态+版本条件更新；已开始产生外部副作用后可能只能“尽力取消/补偿”，接口必须返回真实状态，不能一律成功。
- 多调度器：允许重复发现，靠原子条件领取/租约版本决定有效所有者；锁不能替代外部幂等和旧工作者隔离。
- 发送窗口崩溃：保存可重扫事实或outbox，重启重新发送；重复是可设计处理的代价，先删除再发造成的静默遗漏更难恢复。
- 时钟与老数据：壁钟回拨后重新判断绝对due_at并监控偏差，进程内等待不据此累加两年；payload带schema版本和兼容迁移，无法解释的老任务进入可追踪异常而非丢弃。

**常见失分：** 一个 Redis 有序集合就宣称解决所有可靠性；线程 sleep 两年；每秒全表扫描；认为 cron 精度就是任务完成精度；没有过期恢复或取消版本控制。

**练习与岗位映射：** 用可注入时钟与持久化小任务表实现缩短版模拟，两年仅映射为远期数据，不实际等待；注入领取后崩溃、完成前 ACK 丢失、重复扫描、时钟跳变、取消竞态。检验“所有已接受任务最终处于可解释终态或可追踪待办”，而不只断言运行次数。Python 后端展示事务边界，测试开发展示确定性时间测试，AI 工程关注延时评估/清理任务、版本化输入与重复调用成本。本次未执行该系统练习。
