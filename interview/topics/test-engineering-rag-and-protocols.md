## 一、如何设计一套 RAG 评测方案？

与[AI应用工程中的RAG定位](ai-application-engineering.md)交叉阅读；这里专门展开测试开发的评测契约与质量门禁。

### 题意与岗位背景

扩展问法：“知识库问答上线前如何验收？”“回答错误怎样区分检索问题和生成问题？”“换 embedding 后平均分变高，能否发布？”面试考察的不是能否背出评测工具，而是能否把概率系统拆成稳定可观测的环节，并设计有可信判定依据的回归测试。

### 答题框架

可先用一分钟回答：“我会先明确用户、任务与不能发生的错误，再建立带证据和权限标签的评测集。检索层看证据是否找到、排序是否合理，生成层看回答是否正确、完整、有依据，系统层同时看延迟、成本、安全与拒答。离线通过后再小流量验证线上效果；每次失败都能定位到数据、检索、上下文构造或生成环节，而不是只给一个总分。”检索过程与系统回答分开评测，有微软官方 RAG evaluator 分类作为参考。[R1]

1. **先定任务契约。** 是客服 FAQ、内部政策查询，还是多文档归纳？回答需要哪一天的版本？允许使用模型常识吗？何时必须拒答或追问？例如“只能根据当前租户的有效制度作答并附出处”，与开放域百科的验收标准完全不同。
2. **建分层样本集。** 每例记录 query、身份/租户、知识库快照、相关文档与证据片段、预期关键事实、允许的回答范围、是否应拒答。覆盖单跳、多跳、同义改写、缩写、错字、长问题、多轮指代、时效冲突，以及库内无答案和权限不足。复杂问题可标注多个可接受证据集合，避免把唯一措辞误当标准答案。
3. **检索层。** 明确按文档还是 chunk 计分。Recall@k 衡量标注相关项被找回多少；Precision@k 衡量返回项的相关比例；MRR 关注首个相关结果位置；NDCG 适合分级相关性。多跳题额外统计“完整证据集合命中率”，否则命中一篇却缺关键前提，指标看似不错仍答不出来。标注不完备时，不能把所有未标注文档直接视为不相关。
4. **生成层。** 正确性看是否符合经核验的事实；忠实性看主张是否获输入证据支持；相关性看是否回答所问；完整性看关键点是否遗漏；引用质量检查出处确实存在、用户可访问且支持相应主张。忠实于过期文档也可能事实错误，正确结论也可能引用伪造，不能混成一个维度。[R1][R2]
5. **系统层。** 记录检索、重排、首 token、总耗时与 P95/P99，区分冷启动和稳态；记录 token/调用成本、失败率、拒答率、越权泄漏率。质量门槛按业务确定，不能套用通用“超过 90 分即上线”。涉及权限的失败应独立作为发布阻断项，不让高平均质量掩盖风险。

### 原理、权衡与故障定位

调大 top-k 可能找回更多证据，也可能引入噪声、矛盾、延迟和上下文截断；大 chunk 保留上下文却降低定位精度，小 chunk 更精确但容易切断条件。重排改善排序但增加时延，不能只报告质量收益。推荐固定生成配置，分别替换检索结果为真实检索与人工证据：前者差、后者好，优先排查召回/重排；两者都差，检查提示、上下文组织、模型能力或题目标签。再固定证据只换生成设置，避免同时改五个参数而无法归因。

LLM-as-judge 适合扩大覆盖，但不能当无误差裁判。建议写明确评分量表与反例，先由人工双标一批，再比较一致性；盲化版本，调换 A/B 顺序，检查裁判是否偏好长答案或特定措辞。对于日期、金额、枚举、引用有效性可优先用规则判定；开放文本再用模型和人工。相同输入多次运行报告分布，不把一次采样的提升当确定结论。微软亦提示生成非确定性与实验参数留档的重要性。[R2]

### 高频追问及回答方向

- **没有标准答案怎么测？** 先让领域人员标少量高价值案例，建立可信基线；可用 query-context 相关性和回答忠实性做弱监督，但这些不能证明真实正确。线上失败转人工审核后再进入回归集，避免系统给自己出题、给自己评分形成闭环偏差。
- **怎么防评测泄漏？** 开发集用于调参，冻结测试集只用于验收；按原始文档、时间或业务来源分组切分，避免近重复改写跨集合。RAG 的测试问题所需证据本来可以存在知识库中，这不等于泄漏；把测试问答及标签灌入训练/调参流程、反复针对测试集优化才是另一类问题。
- **无答案与权限不足怎么区分？** 允许访问的材料不足时，应表达无法确认或请求澄清，不披露是否存在用户无权查看的文档。评估拒答的 precision/recall，同时统计有答案题误拒与无答案题编造。权限过滤必须基于服务端确认的身份，不能信任用户传来的 group_id。[R3]
- **离线涨分线上变差怎么办？** 检查问题分布、检索索引时效、缓存、负载和真实多轮行为。在线小流量按用户/会话分桶，关注解决率、转人工率和纠错反馈，配合延迟、安全护栏；点击率或点赞率不能单独替代正确性。保留可回滚版本和失败 trace。

### 边界与故障测试

建议建立五条故障链：①空库、向量服务超时、索引局部更新，是否稳定降级而非胡编；②新旧制度冲突、删除文档仍残留缓存，是否给出正确有效版本；③跨租户相似文档、权限刚撤销、引用链接绕过鉴权，正文/标题/摘要/缓存均不泄漏；④检索材料含“忽略之前规则”等指令，模型是否将材料当证据而非执行命令；⑤超长证据截断、多轮历史污染、重复召回，答案是否遗漏限定条件。日志也要脱敏并限制访问，不能为评测制造新的泄漏渠道。安全过滤只是实现手段，不代替身份验证和端到端权限检查。[R3]

### 建议实验（未执行）

用合成的产品规则搭建 60 条小样本：30 条直接问答、10 条多证据、10 条无答案、10 条权限/版本冲突。冻结语料和标签；比较两种 chunk 策略与两个 top-k，先不更换模型。每例保留召回列表、重排结果、实际送入模型的上下文、回答、引用、阶段耗时与裁判理由。输出分层结果和至少五个失败案例，而不是只展示总分。样本量用于练习，不足以声称达到生产可靠性；不应把建议实验写成个人已做过的项目。

## 二、WebSocket 原理与测试如何回答？

[TCP与业务幂等](networking-and-protocols.md#n6)提供底层边界，本节把它应用到聊天室的连接与消息测试。

### 题意与岗位背景

原始转述只确认“WebSocket”主题。扩展问法：“与 HTTP 有什么关系？”“消息为什么丢了？”“怎么压测聊天长连接？”重点是区分连接、协议帧和业务消息，并知道一个成功握手不代表业务链路可靠。

### 答题框架与原理

先界定场景：“对于双向、频繁、实时交互可考虑 WebSocket；只需要服务器推送时也应比较 SSE，不必一律上长连接。测试按握手、消息、断线恢复、安全、容量五层展开。”

以 **HTTP/1.1** 场景解释：客户端发 Upgrade 请求，服务端接受后返回 101 并校验相应握手字段，之后按 WebSocket 帧交互；客户端核对服务端返回的 Sec-WebSocket-Accept，以验证协议握手，不能替代用户鉴权。帧包含操作码等信息，一条消息可拆成多个帧。客户端到服务端使用掩码，掩码不是加密；机密性依赖 TLS，即 wss。协议包含 Ping/Pong 与关闭控制帧。[W1]

不要说“WebSocket 永远先 GET 再 101”。HTTP/2 可用扩展 CONNECT，在一个流上建立 WebSocket；这是不同的引导机制，不能照搬 HTTP/1.1 的连接级 Upgrade。[W2] 面试中先讲常用路径，再说明版本边界即可，不必展开所有扩展。

### 可靠性与工程权衡

连接内的传输有序，不等于业务事件恰好处理一次。服务端落库成功后 ACK 丢失，客户端重发会重复；连接断开后重建，旧连接的数据不会自动补发。建议业务消息带 message_id、会话内序号及确认位置，客户端基于 ACK 决定重试，服务端以幂等键去重，并约定补发窗口、序号范围和状态保存期限。“已收到”“已持久化”“对方已读”是不同 ACK，必须写进契约。端到端效果依赖存储事务与去重策略，不能承诺靠 WebSocket 得到 exactly-once。

重连使用指数退避和随机抖动，避免节点恢复时连接风暴；明确鉴权失败等不可重试错误，网络恢复后重新鉴权和订阅。多设备、多节点、离线消息需要会话路由与状态设计；粘性会话能减少路由开销，却不能代替故障后的状态恢复。心跳间隔要兼顾 NAT/代理空闲超时、耗电与开销，不能照抄固定秒数。

浏览器原生 WebSocket API 不提供自动背压，发送排队可查看 bufferedAmount，但这不等于接收端有背压。应限制队列、消息大小及订阅速率；行情最新状态可合并，账务事件则不能随意丢弃，需暂停、补拉或明确失败策略。[W3]

### 高频追问及回答方向

- **TCP 可靠，怎么还有丢消息？** TCP 保障连接中的字节传输，不保障进程处理完成、落库成功或断线后的重放。用业务 ACK、持久化位置和消息 ID 对账区分“未发出、已到达、已处理但确认丢失”。
- **心跳通过能说明业务健康吗？** 只能提供有限的连接活性证据，业务线程或下游数据库仍可能阻塞。需另测业务往返、消费滞后和队列深度。浏览器 JS 不能像普通消息一样直接操作协议 Ping/Pong，需要时定义应用层心跳，并避免混淆两者。
- **如何判定有序？** 先问顺序范围：单连接、单会话、单用户还是全局。多连接并发、异步处理和重放可能改变业务到达顺序；测试按约定的序列维度断言，不对未承诺的全局顺序作要求。
- **是否只测连接数？** 不够。十万空闲连接与十万活跃连接是不同负载，需要连接建立速率、消息大小/频率、广播扇出、慢消费者比例与重连峰值。指标包括成功率、端到端延迟分位数、内存/FD、发送队列、消费滞后和恢复时间。

### 边界与故障测试

协议层测试不支持的子协议、畸形帧、非法 UTF-8、超大消息、连续分片与控制帧穿插、双方同时关闭；期待按协议拒绝或有界处理，而不是崩溃和内存无限增长。应用层测试空内容、重复 ID、旧序号、断线前后重发及超出补发窗口。网络层覆盖半开连接、代理空闲清理、网络切换、丢包和节点滚动发布。压力测试分“建连、稳态、广播、慢消费、恢复”几阶段，记录成功样本以外的超时和失败，避免只看成功请求延迟。

安全层使用 wss，校验允许的 Origin，但不能把 Origin 当身份认证；登录后仍需逐条操作鉴权，订阅房间/租户不能只靠前端限制。测 token 到期、登出撤销、跨站发起连接、越权订阅和消息注入。限制连接数、速率与消息大小；认证材料不要进入 URL 和普通日志。OWASP 对 Origin、会话失效、消息级权限与资源限制提供了专项清单。[W4]

### 建议实验（未执行）

搭建一个最小聊天演示，定义“ACK 代表已持久化”。客户端发送 1000 条唯一 ID 消息，分别在发送前、落库后回 ACK 前、ACK 后断网。重连并补发后核对唯一消息数、重复处理数、顺序与恢复耗时。再引入慢消费者与服务端重启，观察队列是否有界。实验价值在可重现故障及状态对账，不在连接数夸大；只在授权隔离环境开展压测。

## 三、HTTP 方法、状态码、缓存、幂等与版本测试

### 题意与岗位背景

原始转述仅有“HTTP”，无法推出具体问法。备考扩展限定为接口测试最常见的契约：请求如何表达意图、失败如何表达、缓存是否正确复用、重试是否造成重复写入，以及不同传输版本是否改变业务语义。

### 答题框架与关键原理

“我先从方法和资源契约说起，再用状态码与响应头判断结果；缓存与幂等重点看重复访问和失败重试；最后说明 HTTP/1.1、2、3 的传输差异不应改变同一接口的业务含义。”

- **方法与幂等。** 安全指请求语义不要求改变资源，不等于服务器完全不记日志；幂等指相同请求重复执行的预期效果与一次相同，不要求返回码一致。PUT、DELETE 具有幂等语义，POST 不天然幂等，PATCH 也不能一概视为幂等。首次 DELETE 成功、第二次返回 404 仍可幂等。[H1]
- **状态码。** 不把所有成功都写 200：创建与异步受理分别考虑 201、202，202 不证明任务最终成功。区分未通过认证的 401 与拒绝访问的 403；409 用于冲突，412 表示条件不满足。测试状态码、响应头、结构与实际副作用，不只断言 code=200。[H1]
- **缓存。** max-age 控制新鲜期；no-cache 允许存储但复用前需验证，no-store 要求不存储；private 限制共享缓存。ETag/If-None-Match 可参与再验证；304 不是重新发送完整正文。Vary 影响选取缓存表示，忽略它可能把语言或编码版本串用。[H2]
- **版本。** HTTP/1.1 常用持久连接，但并非等同于多路复用；HTTP/2 将请求映射到流并在连接上复用，仍可能受 TCP 丢包引起的连接级阻塞影响；HTTP/3 基于 QUIC，降低跨流的传输层队头阻塞，不能宣称完全没有阻塞或所有网络都更快。[H3][H4]

### 原理权衡与追问

**POST 超时能不能重试？** 超时只是客户端没看到结果，不证明服务端未执行。对创建订单等接口，可设计业务幂等键，作用域包含调用主体与操作，保存请求摘要及处理状态；同键不同参数要明确拒绝，不能复用旧结果。并发请求要靠原子约束或事务，不能“先查不存在再插入”而没有竞争保护。键过期后可能再次执行，因此保留期、重试窗口和业务唯一性要协调。这是应用设计建议，不是 HTTP 自动提供的保证。

**怎么避免更新覆盖？** 先读资源版本或 ETag，更新时带 If-Match；不匹配返回 412，再让客户端重新读取或合并。测试两个客户端同时读旧版本，一个更新后另一个不能静默覆盖。仅有幂等不能解决并发丢失更新。[H1]

**接口数据变了为什么还看到旧值？** 按浏览器、本地客户端缓存、CDN/代理、源站逐层看 Age、Cache-Control、ETag、Vary 与实际缓存键。区分合法的新鲜期内复用、再验证错误和失效传播延迟。不要简单用“随机参数绕缓存”当修复，否则只遮蔽故障。

**HTTP/2 一定比 1.1 快吗？** 不一定，取决于请求规模、连接复用、服务端处理、网络丢包与配置。性能实验需固定负载和网络，记录实际协商协议，避免把 TLS 握手、DNS、连接冷启动混进同一结果。版本升级仍需验证网关、代理、超时和流限制的兼容性。

### 边界与故障测试

按四组组织，避免无限扩展网络知识：①契约：错误方法、缺参数、空值与超限、编码、错误媒体类型；验证错误响应稳定且无敏感堆栈。②重试：请求已提交但响应丢失、同键并发、不同账号同键、同键不同内容、幂等记录过期与服务重启。③缓存：首次访问、未过期命中、过期后 304/200、资源变更、Vary 维度、私有数据在多用户之间是否串用；不能假设有 Cookie 就天然不会被共享缓存。④版本与链路：代理超时、连接关闭、单流取消、并发流上限、服务降级；验证重复写入和请求取消后的实际状态。

### 建议实验（未执行）

建立三个小接口：可缓存的公开商品、带 ETag 的库存资源、带幂等键的订单创建。用请求记录展示缓存命中与再验证；让两个客户端竞争更新库存；让订单服务在提交后丢弃响应，再重试核对唯一订单数。验收输出包含请求/响应、最终数据库状态、并发时序和失败原因。实验中不要使用真实支付或个人数据，也不要声称 HTTP 本身提供了业务事务。
